# 订阅管理功能拆解与本地化方案

> 2026-10-28最新调整：详情只保留基本信息、备注与“聊天／编辑／删除”；移除账单入口、归档功能、变更记录界面和提醒配置说明。取消续费显示在下次扣费位置，默认三天一次的后台提醒保留。旧数据和内部必要快照不清除，当前流程见[订阅主界面](../design/subscriptions-ui.md)。
订阅管理用于集中查看上个月的消费、本月预计总消费，以及当前持续中的订阅。mebot 采用手机本地管理：列表、编辑、日期计算、费用汇总和已登记提醒独立运行；AI 谈话按需调用模型，文字与截图一起接入聊天创建。

新版保留订阅历史、变更记录和聊天历史；每个周期在到期日或预计自动扣费日前 3 天只提醒一次。AI 采用与日程一致的单会话处理单条业务的方式：一个会话只处理一个订阅，新开会话对应一份新订阅草稿及独立聊天记录。

Matrix、R2 和服务端运行组件从新功能的迁移范围中移除。2026-10-27 用户调整为仅通过聊天创建卡片，移除手动新增入口；底栏已从预览接为真实文字／截图提取、缺失追问、会话内确认保存与本地历史，见 [订阅主界面](../design/subscriptions-ui.md)。第 1 至 5 阶段的本地存储、管理、账务统计和聊天创建已接入，见 [订阅本地存储基础](../development/subscriptions-storage.md)。14→15 的唯一迁移保留旧数据，后续账务与聊天沿用冻结结构。第 6 阶段已接入独立本地通知与后台恢复，采用经协调的 15→16→17 连续迁移。

## 迁移时需要修正的行为

### 费用统计应区分预算和真实支出

旧版实际报表只筛选当前扣款日期，没有扣款确认、金额快照或历史流水。日期推进后，同一月份的报表会改变；日付和周付也只取每条订阅当前的一次金额。依据见 get_billing_in_month 和 get_monthly_report。

新方案区分三种口径：

1. 平均月费：用于估算长期预算，年付等折算成月均支出，并标明折算规则。
2. 当月预计扣款：按所选月份和计费规则枚举各次计划，周付、日付可以有多次。
3. 已确认支出：仅来自用户确认的扣款流水，保存当时金额、币种和日期，后续修改订阅不能改写历史支出。

旧版使用固定汇率，未知币种按 1 处理，周付乘 4.33、日付乘 30，见 display.py。首版建议按币种分别统计；若增加统一币种总计，需显示汇率来源或用户设定值、日期及未换算项目，避免把估算显示为精确扣款。

### 续费计划与历史记录分开

到期推进仅更新预计日期，不意味着已成功支付。登记关闭续费后，保留有效期；当前有效期结束前仍可收到本期的一次到期提醒，到期转归档，停止生成未来扣款计划。主动删除另设明确入口，不沿用后台到期清除记录。

历史记录作为核心功能保留，包括订阅创建、金额与日期等字段修改、关闭或恢复续费、周期推进和到期归档的记录。每次变更保存发生时间、操作类型及对应字段的前后值或版本快照，不能只覆盖当前状态。到期、归档、退出页面或重启应用都不清除订阅历史和聊天记录；详情可以回看已结束的订阅及其变更过程。用户主动删除时明确展示删除范围，避免将归档等同于彻底删除。

聊天历史保存用户与助手消息、待确认内容、关联操作及真实执行结果。业务变更历史与聊天历史通过订阅和会话关联，但业务状态仍以结构化记录为依据。历史保留不等于推定已成功扣款，已确认支出仍须有独立的真实扣款记录。

自然月计算需要保存原始日期锚点。例如每月 31 日的订阅遇到 2 月可落在月底，下一月应按锚点恢复到 31 日；如果用户选择的是“每月最后一天”，则持续按各月最后一天计算。跨年、闰日和长期未启动后的推进都由本地规则处理。

旧版 `custom` 只是标签，既无间隔字段，也不会自动推进。若保留自定义周期，需要明确“每 N 天”或“每 N 个月”等可执行规则；否则只记录一个到期日，由用户手动续期。

### 每个周期提前三天只提醒一次

旧版 get_upcoming 实际匹配 `today + 5 天` 这一个日期；check_reminders 在消息送达前就写入已发送标记。重启错过检查日或发送失败时，可能漏掉提醒。

新版固定提前 3 天，按以下目标生成本期唯一提醒：自动续费订阅采用预计自动扣费日；不自动续费或已登记关闭续费的订阅采用有效期结束日。两种目标属于同一周期时只选一个，不分别发送到期和扣款通知。永久且无到期日的订阅不生成提醒。

“只提醒一次”按订阅的每个计费或有效周期计算：Android 提交本期通知后不在前 1 天、到期当天或每天追加提醒；后续进入新周期时，该周期可再提前 3 天提醒一次。首版提供提醒开关与通知时刻，不设置多档提前量；默认 09:00，可在详情调整提醒时刻。

本地提醒保存订阅 ID、稳定周期 ID、目标类型与日期、提前 3 天的计划时刻、业务版本和交付状态。去重以订阅 ID 与周期 ID 为依据，业务版本用于阻止旧任务执行。新增、修改日期、登记关闭或恢复续费、归档或删除后，取消失效计划并重新核对；同一周期修改日期或通知时刻不重置已经交付的状态，切换目标类型也不新增一次提醒额度。

采用 Android 本地通知与可恢复调度。开机、应用重开及日期时区变化后恢复尚未交付的有效计划；若已进入提前 3 天的提醒窗口但尚未到目标日期，可补交本期尚未成功交付的一次通知。错过多个周期不密集追发旧通知。通知使用稳定标识配合持久化去重；提交中断后能核实仍存在的同标识通知则补记，无法核实则标为不确定且不自动重发。页面刷新、切换会话、重启或关闭后重新开启提醒都不能重复通知已交付的本期提醒。权限不足、调度失败和通知提交失败记录真实状态，不预先标为已交付，重试仍遵守本期只有一次的约束。

### 写入由本地代码控制

旧版提示词要求删除确认，但 delete ID 直接执行；按名称删除 会删除所有同名项。新实现由本地页面确定目标 ID、展示确认，并在数据层校验权限范围、字段和记录版本，不能只依赖模型承诺。

待确认字段、输入草稿和消息按会话持久入主库；确认操作使用去重标识并在事务中提交。首次确认创建订阅时，同时完成会话绑定与操作结果登记，重复点击或重试不会重复新增，也不会把会话绑定到第二个订阅，保存成功后才显示完成。模型失败保留消息、输入和截图，可在原会话重新解析；不提供手动创建表单。普通查询与提醒直接读取结构化业务数据。

旧版每次模型提取会携带完整订阅、常用账号和支付渠道，见 extract_subscription_mutation。新实现仅提供当前会话的输入、草稿、关联订阅和完成本次操作所需的本会话历史，不自动附带其他订阅、会话或全量历史；具体隔离规则见下文。

## 建议的本地使用流程

### 订阅首页

顶部同一张汇总卡片左侧突出本月预计总消费，右侧用较小字号展示上月消费与年月，持续订阅数量放在本月金额下方；不提供“即将扣费”“历史”按钮，也不显示预览提示文案。主列表仅显示持续中的订阅，按预计扣款日期排列，永久项目单独标识，卡片不显示右箭头但整卡可点击。已登记关闭续费但尚在有效期内的项目继续展示，到期归档后移出主列表；历史记录和聊天仍保留，既往消费仍计入其实际发生月份。详情从底部弹出，展示完整信息并提供相关业务操作。

新增统一通过 AI 谈话，文字和截图均从底栏发送；先建立独立会话和草稿，缺失信息就在聊天里追问。提取完整后展示待确认卡片，用户确认创建或回复“确认”后由本地事务保存；修改提取结果仍用继续聊天，不提供手动创建表单。账号、支付渠道可留空后补充。已有卡片的本地编辑和扣费登记继续保留，模型不可用时可以管理、查看和计算已有数据，新的提取请求可稍后重试。

### 一个 AI 会话只处理一个订阅

采用与日程相同的单会话处理单条业务方式。新开会话创建一份新的订阅草稿和独立聊天记录，不继承其他会话的消息、待确认操作或订阅绑定；未确认保存前只存在草稿，不自动生成正式订阅。

用户确认后，会话固定关联该订阅。后续补充账号、修改金额或日期都在同一会话中提议和确认，续费进入新周期也继续使用该会话，不按周期另开聊天。关闭及恢复续费也可在详情明确登记；不会替用户操作服务商。再次从订阅进入 AI 时恢复原会话和历史；此前已有且尚无会话的订阅首次进入时绑定专属会话。新建会话保留旧草稿和消息，可从会话记录重新打开。

同一会话不能切换到另一个订阅，也不批量创建或修改多条订阅。用户在当前聊天中提到另一个服务时，引导新开会话；一条输入包含多个订阅时，先明确本会话要处理的那一个。跨订阅的列表、搜索和汇总由本地页面提供，当前 AI 会话只操作自己关联的订阅。

每个已绑定会话只关联一个订阅，已建立的订阅复用自己的专属会话。模型上下文包含该订阅的最新结构化状态、当前草稿、待确认操作和必要的本会话历史；完整历史在本地按需加载，不要求每次请求全部发送。切换会话、退出或重启后，消息、未发送输入和待确认内容保持各自独立，模型结果也必须校验目标会话，不能写入用户后来打开的其他会话。

### 统计与通知

首页显示上月消费和本月预计总消费，不增加统计切换入口。本月预计总消费覆盖整个自然月的各次扣费计划，已确认扣款使用历史快照覆盖对应计划，其余计划按本地规则估算，同一扣费事件只计一次；不是截至今天已经扣费的总额，也不是按年费除以十二得到的平均月费。日付、周付在月内发生多次时分别计入，取消或结束规则截断未来计划。

上月消费读取对应自然月的已确认扣款历史，保存各次扣款的日期、金额和币种快照；订阅取消、到期归档或后续改价都不能改写过去月份。没有实际扣款证据时显示“暂无记录”，不从预计日期或当前价格生成付款成功记录。多币种分别汇总。第 3 阶段已接入真实统计和每项订阅的按月流水弹层，支持确认、更正、撤销及重新确认；显式更正保存原值、新值和操作记录，不能与普通订阅编辑混用。关联周期的付款与计划去重，额外扣费独立计入；实际日期决定归属月份。

通知展示服务名、适用的预计金额和币种，以及到期日或预计自动扣费日，点击进入对应订阅详情并可打开其原会话；每期提前 3 天只通知一次。用户关闭系统通知后仍可保存、查看和编辑订阅，页面展示实际提醒状态。

页面切换、详情开合、筛选、输入方式切换及列表变化采用与现有 mebot 一致的过渡动画；保留滚动位置，兼顾字体缩放、连续点击和取消操作。

## 本地数据与工程落点

所有结构化记录进入现有 `mebot.db`。主库 14→15 已由集成会话唯一预留并批准本分支实施，正式注册 9 张新表及索引，原 36 张业务表与历史 schema 保留。独立测试夹具继续用于事务边界验证，正式迁移另有真实 Room 升级和回滚测试，不创建第二个运行时业务库。

| 数据职责 | 拟保存内容 | 建设阶段 |
| --- | --- | --- |
| 订阅记录 | ID、名称、账号、渠道、定点金额、币种、周期、日期锚点、预计扣款日、有效期、状态、时间与版本 | 核心功能 |
| 订阅变更历史 | 订阅 ID、发生时间、操作类型、字段前后值或版本快照，保留已结束订阅的历史 | 核心功能 |
| 输入草稿与业务操作 | 表单或提取草稿、会话 ID、目标订阅 ID、确认状态、去重标识、执行结果 | 核心功能 |
| 提醒设置与计划 | 开关、通知时刻、稳定周期 ID、目标类型与日期、固定提前 3 天的计划、订阅版本、调度及交付状态 | 核心提醒；同一订阅同一周期只能有一份有效交付记录 |
| 会话与消息 | 会话 ID、唯一订阅绑定、消息、未发送输入、待确认草稿和关联操作；新建草稿阶段尚未绑定正式订阅 | 核心功能；确认保存时建立一对一绑定 |
| 截图关联 | 本地媒体 ID、订阅或草稿关联、名称与顺序；文件复用可靠本地存储 | 选择保留截图时增加 |
| 扣款流水 | 所属订阅、确认日期、金额和币种快照、说明与去重标识 | 支撑上月消费，以及本月预计总消费中已确认的部分 |

预计扣款和汇总是可重建结果，业务记录、变更历史、聊天记录及真实扣款流水为原始数据。更新订阅当前状态、追加变更历史和登记操作结果在同一事务中完成。删除、编辑或归档后同步失效派生结果和提醒，历史查询不能从过期缓存恢复有效记录；到期与归档不删除原始历史。截图清理要检查跨 Bot 引用，不能因删除订阅而删除仍被其他记录使用的文件。

实现沿用现有 app 模块，按 `data/local`、`data/subscriptions`、`domain/subscriptions` 和 `ui/subscriptions` 分工，使用 Repository、ViewModel 和 Compose。可复用模型安全设置、本地媒体保存与后台恢复经验，订阅提醒保持自己的业务状态和通知渠道。首页、导航、`AppContainer`、主库及跨 Bot 文件清理涉及公共范围，实施时统一协调。

旧数据导入作为可选独立任务：用户主动选择导出的订阅 JSON，先预览、校验和去重，再事务写入。不自动扫描旧运行目录，不导入 Matrix 凭据、R2 凭据、聊天或下载缓存；旧记录不能补造已经发生的扣款流水。

## 建议实施顺序与验收

| 阶段 | 建设内容 | 主要验收 |
| --- | --- | --- |
| 第 1 阶段 | 本地实体、DAO、事务、变更历史、扣费流水、独立会话草稿与图片关联 | 已接入 schema 15 主库；重启恢复、去重、隔离与回滚经过 SQLite 测试，正式迁移保留旧 Bot 数据 |
| 第 2 阶段 | 真实列表与详情、编辑、登记关闭及恢复续费、归档删除、周期日期规则 | 已实现本地管理；原手动新增已按最新要求移除，由聊天创建替代；已有记录的离线管理及历史保留 |
| 第 3 阶段 | 实际扣费登记、更正、撤销及重新确认，上月消费、本月预计总消费 | 已实现；全自然月计划与确认事件跨月去重，日付周付多次计入，普通改价归档不改历史，多币种不混加，操作原值与草稿保留 |
| 第 4 阶段 | 将真实会话、草稿、消息与截图存储接入共用输入界面 | 已接入；新开会话对应独立草稿，订阅重进恢复原会话，退出重启保留输入、历史和原图，各会话互不混用 |
| 第 5 阶段 | AI 文字与截图提取、缺失追问、确认后创建或修改 | 已接入；仅发送当前会话所需上下文，本地校验后确认保存，失败保留并可重试，确认幂等，不设手动创建入口 |
| 第 6 阶段 | 固定提前三天的一次本地通知、到期维护和恢复 | 已接入；同一周期改期、重试、重启不重复，下期可再提醒一次；旧任务失效；权限不足不影响本地管理；点击通知进入对应详情 |

旧 JSON 导入作为后续独立可选任务，不阻塞核心截图创建与本地管理。

每批应用实现完成后，在所属 worktree 运行相关测试、Lint 和构建，使用共享安装锁核对版本、签名和持久数据兼容，再安装本分支预览，由用户完成具体手机体验与回归测试。

第 2 阶段分支包启用 schema 15 与真实手动管理，第一次安装后冻结结构；其他旧分支再次装机前须同步兼容基线。第 3 阶段保持表结构、迁移及媒体格式不变，增加扣费操作语义和派生统计，按项目规则完成分支检查、构建与覆盖安装。需要保留新的更正／撤销历史时，预览来源须包含对应操作类型的读取代码。

第 6 阶段默认09:00、提前三天；普通通知使用独立渠道和可恢复闹钟，不要求日程的精确闹钟权限或持续响铃。详情展示实际权限、计划及提交状态，系统可延后调度。非自动续费的日期更正保留本期额度，明确“登记已续期”或聊天确认新的续期后才开始新一期，不自动新增扣费流水。首次安装 schema 17 后，其他分支必须先同步兼容基线再轮换安装，保留全部旧表与文件。
